**发现与影响**

**优先问题：缺少企业资料时仍生成无依据的人员事实。** T1-S3 两份正文第 3 行分别声称“全部为投标人直接聘用并依法缴纳社会保险的在职员工”和“全部成员均为投标人正式在职人员，社会保险缴纳单位名称与投标人全称一致”。这些是企业现状事实，不能由招标要求推导；本次已确认企业资料为 0，知识库与全局事实也为空。名称或证书编号留空，并不能使上述肯定性断言成为待核实表述。两份正文规则阻塞均为 0，智能完善在 0 轮修订时标记目标达成。抽查结论不替代完整人工标注，建议在资料不足时强制将此类声明改为明确的待核实状态。

1. **评分要点检查出现可复现误报。** T1-S1 单次正文已在第 98、108 行分别写出硬件和软件运维方案，并有详细措施，仍被判缺失“软、硬件的运维方案”。`scoring_coverage.point_overlap` 得到 0.6，低于 0.7 阈值；顿号被当作二字片段的一部分。最小输入 `硬件运维方案：设备健康监测与备件更换。软件运维方案：系统补丁与数据库巡检。` 也返回未覆盖。对应源代码 `backend/app/services/checker/scoring_coverage.py:42`、`:57`。
   同类问题也出现在 T1-S2：评分点“风险的防范和应对”被判缺失，但第 119 行标题为“风险的防范与应对”，随后有风险登记、分类防范措施和动态管控三段内容；仅匹配到 0.5。至少这两处自动阻塞不能按真实遗漏计算。
   **另有占位符漏报：** T2-S2 单次正文第 3 行包含 `【投标人全称：待填写】`，章节检查和导出预检均只匹配以“待填写/待核实”开头的括号内容，漏掉此写法。最小复现：将 `我方（【投标人全称：待填写】）` 传给 `export_preflight._placeholders`，得到 `status=ok, count=0, message=正文中没有占位`。源代码 `backend/app/services/checker/export_preflight.py:14`、`section_check.py:38`。
2. **误报触发了额外模型修订，并扩大篇幅。** 同一章节的智能完善初稿已含“软硬件运维方案”及软硬件详细措施，但前两版均报缺失，第二轮改用“软、硬件运维方案”后才消除阻塞。最终 7,224 字，预算 4,900 字，超出约 47%；仍有 1 项质量问题，却按当前策略标记为目标达成。这说明规则计数改善不能直接等同于实质质量改善。
3. **长章节出现输出截断和放大额度重试。** 已恢复的截断请求计入实际请求数与 tokens，不视为零成本成功；完整状态数见上表后的调用记录。
4. **真实资料覆盖有限。** 当前知识库为空，已确认企业资料为 0，16 条示例资产不参与生成，全局事实未填写。本次检验了资料缺失时的产出行为，不能据此认定真实企业事实、检索召回或证明材料齐备；人工事实核验列保持未填写。
5. **非阻断警告。** 前端组件测试有图标解析警告；应用入口实际有全局图标注册，现有证据不足以认定为生产故障。构建提示部分资源包超过 500 kB，主包约 1.22 MB，最大 Mermaid 相关包约 1.45 MB。
